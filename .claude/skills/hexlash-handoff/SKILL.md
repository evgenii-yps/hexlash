# hexlash-handoff — работа по эталону

## 1. Что такое хэндоф

Хэндоф — рабочий HTML/JSX-прототип экрана, лежащий в `docs/design-handoff/`. Это **источник правды по числам** для конкретного экрана: отступы, размеры, тени, тайминги.

Что уже лежит в репозитории:

```
docs/design-handoff/
  Hexlash Secondary Buttons.html   — эталон семьи матового хрома
  hexlash_home/                    — дом: HTML + README + home.css + JSX
  mode_select/                     — Mode Select: HTML + README + design-notes.md
  ground_select/                   — Ground Select: HTML + README
  shop_bright/shop_bright_export/  — яркий магазин: HTML + CSS + JSX + палитра
```

## 2. Порядок работы с макетом

1. **Проверь, есть ли макет** для этого экрана в `docs/design-handoff/`.
2. **Прочитай README** рядом с ним, если есть, — там обычно оговорки автора.
3. **Открой сам HTML/CSS** и вытащи числа. Не пересказывай на глаз.
4. **Перенеси 1:1** — отступы, размеры, тени, тайминги, порядок элементов.
5. **Прогони по дисциплине** (`hexlash-design`): бывает, что прототип нарушает правила проекта. Тогда — §5.
6. **Отчитайся, что разошлось** и почему.

## 3. Правило 1:1 — почему оно жёсткое

Дважды в истории проекта экран собирали «по описанию», а не по файлу. Оба раза каркас и дисциплина выходили верными, а **десятки конкретных значений расходились** — и приходилось делать второй проход.

Вывод, закреплённый как правило:

> **Если файл прототипа есть — числа берутся из файла. Не из описания, не из скриншота, не по памяти.**
> **Если файла нет — сначала попроси файл, и только потом собирай.**

## 4. Если макета нет

- **Экран новый и сложный** → скажи владельцу: «макета нет, соберу по ТЗ, но потом почти наверняка будет второй проход на сведение». Пусть решит — ждать макет или собирать сразу.
- **Экран — вариация существующего** → собирай из существующих компонентов (`.hs-chrome`, двери fight-card, карточки `sb-*`). Не изобретай новый компонент.
- **Мелкая правка** → просто делай, макет не нужен.

## 5. Когда расходиться с прототипом — можно и нужно

Прототип — источник **чисел**, а не источник **правил проекта**. Расхождение обязательно в таких случаях:

| Что в прототипе | Что делаем |
|-----------------|-----------|
| Дубль верхней панели (свой бренд/кабинет/back) | Выкидываем — панель в проекте общая `.hs-strip` |
| HUD-уголки на экране | Сняты с экранов (в модалках оставлены) |
| Диагональный срез / уголки на вторичных кнопках | Ретированы 30.06.2026 |
| Второе свечение в покое | Оставить одно, самое главное |
| Розовый на вторичной кнопке | Хром-холодный |
| Нейплейт, «SEASON 0», плашка привязки | Сняты с продукта |
| Свечение на логотипе | Логотип всегда матовый |
| Свой шрифт | Saira Condensed + JetBrains Mono |
| Кривой артефакт прототипа | Опустить и сказать об этом |

**Каждое расхождение проговаривается в отчёте.** Молча не расходимся.

## 6. Уроки из истории — реальные случаи

- **Ground Select.** Первый проход собран по ТЗ, файла в репозитории ещё не было. Каркас и дисциплина верны, эмблемы и десятки значений разошлись. После того как владелец приложил HTML, экран сведён 1:1 вторым проходом. Внешняя гекс-оболочка эмблемы SPACE опущена как кривой артефакт прототипа.
- **Дом (home_controls).** Хэндоф в репозиторий не лёг — строили по описанию плюс сверка точными значениями. Осталась просьба: положить эталон в `docs/design-handoff/home_controls/`.
- **Магазин.** Перенесён 1:1 после того, как хэндоф наконец лёг в репозиторий. Прототиповая дубль-панель выкинута; ранняя попытка перекрасить товар в материалы SAND/RUST была ошибкой и откачена.
- **Экран загрузки.** Собран по брендбуку, а **не** по дисциплине Neon Discipline — осознанное решение владельца: экран ведёт канонизацию нового языка на прод.

## 7. Хэндоф должен лежать в репозитории

Прототип, переданный только в чат, через месяц не найти. Правило:

> **Экран собран по хэндофу → хэндоф кладётся в `docs/design-handoff/<screen_name>/`** вместе с README.

Если владелец прислал прототип в чат — попроси разрешения положить его в репозиторий тем же коммитом.

## 8. Figma

По правилам проекта интерфейс, которого нет в утверждённом макете, **в разработку не уходит**. Если задача про новый экран и макета нет ни в Figma, ни в `docs/design-handoff/` — сначала макет, потом ТЗ, потом код.

Каждое решение по интерфейсу должно жить в двух местах: **макет** (Figma / хэндоф) и **объяснение решения** (Notion, Decisions Log) со ссылкой на макет. Одно без другого не считается завершённым.
