# hexlash-core — операционная база

Читай этот файл первым в каждой сессии. Он не про код, а про то, **как здесь принято работать**.

## 1. Иерархия источников правды

Когда источники расходятся — прав тот, кто выше:

| # | Источник | Что в нём правда |
|---|----------|------------------|
| 1 | **Живой код в `main`** | Что реально работает сейчас |
| 2 | **Notion** (страница «Hexlash» → Snapshot / Decisions Log / Visual System) | Почему так решено, что запрещено, что в работе |
| 3 | **`src/styles/tokens.css` + `src/data/sceneTokens.js`** | Все визуальные значения. Другого набора в проекте нет |
| 4 | **`docs/design-handoff/hexlash_mark/`** | Знак: геометрия и правила. Читается сборкой |
| 4 | **`.claude/skills/*`** (эти скилы) | Правила и конвенции |
| 5 | `CLAUDE.md` в корне | ⚠️ **УСТАРЕЛ** — описывает архитектуру до сброса 01.06.2026. Не опираться. |
| 6 | `skills/` в корне (без точки) | ⚠️ **АРХИВ** — старая система скилов, не читать. |
| 7 | `Hexlash_Combat_System_Documentation.pdf` | Историческая справка |

**Правило расхождения.** Нашёл противоречие между кодом и Notion — **остановись и скажи владельцу**. Не переписывай решение молча и не «подгоняй» код под устаревший документ.

## 2. Что это за проект (в одном абзаце)

Web3-игра. **Игрок — тренер, бойцы — автономные AI.** Игрок задаёт бойцу манеру до боя; в бою боец дерётся сам, игрок вмешивается точечными рычагами. Прод — `hexlash.com` (Vercel, авто-деплой с `main`), бэк — `api.hexlash.com` (Railway).

**Сейчас Этап 1 — Визуализация.** Цель этапа: «работает и считывается» важнее, чем «вылизано». Этап 2 (кошелёк, NFT, платежи, живая экономика) — потом, туда ничего не тащим.

Стек фронта: **Vue 3 + Vite + Three.js напрямую** (не R3F), кастомный i18n (**только en**), Vuex.

## 3. Карта скилов

Загружай по теме задачи. `hexlash-core` — всегда.

| Скил | Когда грузить |
|------|---------------|
| **hexlash-design** | Любой визуальный слой: цвет, шрифт, шкалы, свечение, поведение элементов, движение, объём. Одна инструкция на всё |
| **hexlash-frontend** | Vue-компоненты, роутер, CSS-архитектура, i18n, где какой файл |
| **hexlash-3d** | Three.js-сцены, арена, бойцы, камера, свет |
| **hexlash-combat** | Поведение бойца, намерения, оси, баланс, лаборатория |
| **hexlash-handoff** | Есть готовый макет/прототип в `docs/design-handoff` |
| **hexlash-review** | Перед сдачей работы: самопроверка, доступность, регрессия |

Типовые связки:
- новый экран UI → core + design + ui + motion + frontend (+ handoff, если макет есть)
- новая 3D-сцена → core + 3d + motion + frontend
- правка боя → core + combat
- перед пушем → core + review

## 4. Порядок работы над задачей

1. **Прочитать `hexlash-core` + профильные скилы.**
2. **Понять, что уже есть.** Прочитать существующие файлы по теме. Не изобретать компонент, который уже живёт в `home.css` / `shop.css` / `cabinet.css`.
3. **Проверить эталон.** Есть ли макет для этого экрана? Он источник КОМПОЗИЦИИ — что где стоит и как ведёт себя. Числа берутся из токенов, а не из макета (см. `hexlash-handoff`).
4. **Спросить, если задача ломает принятое решение.** Владелец не программист: спрашивать про продукт («что должно происходить»), не про технику («какую библиотеку взять»).
5. **Сделать минимальную правку.** Не рефакторить попутно. Не «заодно причесать».
6. **Самопроверка по `hexlash-review`.**
7. **Отчитаться в формате из §7.**

## 5. Защищённые файлы

Эти файлы **не трогать без явного разрешения владельца** в тексте задачи. Они несут работающий бой и уже принятую приёмкой моторику; их правка тихо ломает то, что уже одобрено глазами.

```
src/scene/buildArena.js
src/scene/arenaTextures.js
src/scene/arenaPresence.js
src/scene/buildFighter.js
src/scene/ArenaScene.vue
src/scene/hpIndicator.js
```

**Как работать рядом с ними.** Паттерн проекта — **управлять снаружи, а не править внутри**. Примеры, которые уже так сделаны:
- дом гасит разлом, выставляя `riftGlow.opacity = 0` из `HomeScene.vue`, а не правя `buildArena.js`;
- HP-плашка на доме подавлена сканом прямых детей группы бойца снаружи, а не удалением из `hpIndicator.js`;
- режиссёр блужданий `homeWander.js` водит существующую локомоцию снаружи.

Если снаружи никак — **остановись и объясни владельцу, что придётся вскрыть защищённый файл и чем рискуем.**

## 6. Git-дисциплина

- **Работаем в ветке.** Имя вида `claude/<короткое-описание>`.
- **В `main` мержим ТОЛЬКО по явному «мержи» от владельца.** Не автоматически, не «раз всё зелёное».
- Мерж — **fast-forward**, refspec-push без локального checkout.
- **Всегда фиксируй точку отката** — коммит `main`, который был до мержа. Владелец должен уметь откатиться одной строкой.
- Владелец проверяет визуал на preview/проде **глазами**. Пока не проверил — «сделано» не говорим, говорим «готово к проверке».
- Push в `main` напрямую — нет. Никогда.

## 7. Формат отчёта владельцу

Владелец **не разработчик**. Никакого жаргона без расшифровки. Отчёт по задаче — коротко и по этой схеме:

```
Что сделал:      1–3 предложения человеческим языком
Где посмотреть:  ветка / preview-ссылка / какой экран открыть
Что изменилось:  список файлов простыми словами («экран магазина», «стили кнопок»)
Точка отката:    коммит
На что смотреть: 2–3 конкретные вещи для проверки глазами
Не сделал:       что осталось и почему
Риски:           если правка может что-то задеть — сказать заранее
```

Правила общения: объясняй как новичку; не спрашивай про технические детали — выбирай сам и объясняй почему; предлагай варианты **с рекомендацией**, а не «выбирай из трёх».

## 8. Красные флаги — остановись и спроси

- Задача требует второго розового цвета или второго свечения на экране.
- Задача требует править защищённый файл.
- Задача противоречит записи в Notion (Decisions Log).
- Задача тянет функциональность Этапа 2 (кошелёк, реальные деньги, NFT, живая экономика).
- Нужен новый цвет/токен, которого нет в брендбуке.
- Нужна четвёртая тяжёлая 3D-сцена (дом / PVE / арена / пространство — уже много).
- Файл, который нужно поправить, шарится двумя экранами (см. `hexlash-frontend`, §«Ловушки»).
