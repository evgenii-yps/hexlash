## 4. Главный вывод по подходу (виртуальное время)

**Подход ТЗ рабочий, доказано пробой** (`probe-virtual-time.js.txt` — заготовка, которую я гонял; подменяет `requestAnimationFrame`, `performance.now`, `Date.now`, таймеры и `Math.random`).

1. Главный остров под виртуальным временем: два прогона, попиксельная разница **только в области кнопки FIGHT** (x 487–774, y 554–642). Это её CSS-анимация блеска: CSS-анимации идут по времени браузера, а не по подменённому. Вся 3D-сцена совпала. Лечится прокруткой анимаций через Web Animations API (`document.getAnimations()`, `currentTime = виртуальное время`) или через CDP.
2. Арена: бой идёт по-настоящему (ядро, HP 99/90 на снимке `arena-duel-a-8.png`), но два прогона **расходятся** — бой стартует на разных виртуальных кадрах (загрузка асинхронна по реальному времени) и разное число обращений к `Math.random` до старта. **Лечение проверено:** если на входе в `runFight` заново засеять `Math.random`, три прогона подряд дали одинаковые позиции бойцов. Вывод: засевать надо не при загрузке страницы, а в момент старта боя. (Проверено на позициях бойцов на 600-м кадре; побитовое сравнение кадров — задача этапа 1.)
3. Ловушки шага времени (нашли агенты, я проверил часть): шаг брать **16,6667 мс** (а не 1000/60 — игра пропускает кадр, если `time − lastFrame < 16,667`); минимальный первый кадр ≥ 16,67; на шаге грубее 1/24 с сторож пролёта (`transitionFlight`, 3 кадра с dt > 0,05) **обрывает пролёт**; у арены `frameMs/1000` не ограничен сверху.
4. Окружение, которое молча меняет поведение: «уменьшить движение» отключает пролёты, блуждание, груши (не включать); грубый указатель режет до 30 кадр/с (эмулировать мышь); ≤4 ядер или ≤4 ГБ → плотность пикселей режется до 1,5 (подменить `hardwareConcurrency`/`deviceMemory`).
5. Любое синтетическое событие мыши/клавиши во время пролёта **прерывает** его (`flight.skip()`). Посылать нажатия только когда пролёт не идёт.

## 5. По пунктам этапа 0

### 5.1 Кнопка FIGHT — см. раздел 3. Нажатие: мышь Playwright (навести, нажать, выдержать ~120 мс, отпустить).

### 5.2 Пролёт и ворота — проходятся сценарием
Полная цепочка: главный остров → FIGHT (пролёт 3,7 с; камера стартует через 0,18 с) → нажать ARENA на канвасе (нужен настоящий луч: синтетический `pointerup` с координатами; экранные координаты плит не опубликованы — искать наведением, пока не загорится подпись ARENA) → подлёт 2,15 с → занавес → загрузка ворот → подъезд камеры 1,9 с. В воротах: режим → острова бойцов → переключатель `2 V 2 | 3 V 3` (только SQUAD) → объёмная FIGHT → подлёт ~2,15 с → `/play/arena`. С `?dev=1` есть пробы `__gateProbe`, `__gatePick(x,y)` (что лежит под точкой), `__homeProbe` — читают состояние, ничего не меняют.

### 5.3 Камера: подмена без правки сцен
Ни одна сцена не публикует камеру; `OrbitControls` каждый кадр прижимает позу к своему коридору. Поэтому позу надо выставлять **после `controls.update()` и перед `render`**. Два пути:
- **Без правки игры (проверено на жесте):** под dev-сервером (`vite`) у каждой сцены доступен `__vueParentComponent.setupState` (камера, рендерер, бойцы). Оборачиваем `renderer.render`: выставили позу → настоящий `render`. Работает и для защищённой арены. **Не работает на prod-сборке** (`vite build` прячет обработчики) — значит финальный рендер идти должен с dev-сервером. Для нас это приемлемо.
- **Запасной путь:** по одной строке `window.__hexDirector?.(…)` перед `renderer.render` в четырёх незащищённых сценах (Home 1511, Gate 747, Pve 2126, Ascension 266). Только с вашего слова.
- Особенности: у дома ещё идёт покачивание камеры (±4°) и «возврат к стойке» после отпускания; у зала — память камеры и плавный возврат; всё это перекрывается подменой после `controls.update()`. Подписи на экране (DOM) читают настоящую камеру — их прячем.
- Камера арены в DUEL статична, в SQUAD плавно следует за центром живых (`frameLiving`) — подмена её перекроет.

### 5.4 Готовность сцен
Единого события наружу нет (`loadingState` — не на `window`). Признаки для рекордера: нет `#hx-load` и `.hx-loading`; у занавеса `.hx-curtain` нет `is-up`; `window.__hexBootstrapped === true`; с `?dev=1` пробы дают не `null`. Готовность = все этапы + 3 устоявшихся кадра, минимум показа 600 мс, аварийный выход 15 с; всё на реальных `setTimeout`/`performance.now`, то есть **идёт только когда идёт наше виртуальное время**. Пока сцена грузится, время надо качать «вхолостую» без снимков. Экран загрузки игры виден игроку — в ролике его надо заменить чёрным (это и есть «чёрный кадр» из грамматики проекта).

### 5.5 Время и случайность
Симуляция боя идёт **от кадра рендера**, не от часов: `THREE.Clock` (читает `performance.now`) + `rAF`-время. Раздельных скрытых часов нет. `Math.random` — везде (боец: 44 места, удары, уклоны, блуждание; кубик — `rollDie`; противник в DUEL и враги в SQUAD бросаются при монтировании арены). Собственных «засеиваемых» генераторов в бою нет; заготовки `mulberry32` есть только у косметики (разлом, искры), у `transitionFlight` (детерминирован) и у скриптов `scripts/fight-regression*.mjs`. Эти скрипты гоняют бой в Node без сцены, засевают `Math.random` и выдают sha256 — готовая основа для «регрессионного снимка боя и контрольных сумм» из §7 ТЗ (две контрольные суммы — голых ядер и боёв со сборками).

### 5.6 Легенда и SQUAD без модели — A/B/C
- **A. Вход в SQUAD без ворот.** Состояние — в `sessionStorage['hexlash_progress']` (ростер, состав, режим, легенда). Засеивается до загрузки (`addInitScript`), проверено на практике: бой идёт. Легенда: `roster.lg = {id, callsign, core, at}` — настоящего восхождения не нужно, сейф реального игрока не затрагивается (свежий контекст браузера).
- **B. Путь решений легенды без модели есть, но может молчать.** `command.js` — таблица порогов без случайности: легенда действует не раньше 5-й секунды боя, не чаще раза в 3 с; правила — «свой боец < 35% HP → HOLD/TOWEL», «свежий свой (HP>60%) рядом с врагом < 25% → PUSH», «меньше числом → FALL BACK». В ровном 2v2 решений может не быть, пока кто-то не просел. **Для ролика нужно подобрать зерно, при котором решение случится**; строка: `ELDER · HOLD → BLADE` (класс `.cmd-line`). Тумблер `.cmd-toggle` — «I LEAD»/«LEGEND LEADS» (английский; русские «ВЕДЁТ ЛЕГЕНДА» в интерфейсе нет). Он виден только при составе ≥2 (или в SPAR) и сбрасывается на «I LEAD» на старте боя — включать программно после старта (`toggleCommand()` / клик).
- **C. Модель.** При монтировании арены запускается запрос к `/v1/ai/legend-command`. Без токена он падает мгновенно и бой идёт на порогах. **В песочнице запросы наружу заблокированы** (проверено, бой шёл). Для ролика блокируем `**/v1/ai/**` — зависший запрос с действующим токеном недетерминирован.
- **D. Враги SQUAD не задаются явно** (бросаются при монтировании, `composeSquadFoes`): единственный рычаг — состояние `Math.random` на этот момент (засев + подбор зерна). DUEL с заданным противником возможен через SPAR (`services/spar.js`, `/play/arena?spar=1`), но там другое оформление интерфейса.

### 5.7 Легенда над FORGE и груши — без записи в сейф
Состояние читается один раз при монтировании зала. Подмена без записи: менять Vuex-объекты напрямую (хранилище не строгое, `persist` не вызывается) — `store.state.roster.legend = {...}`, для груш у бойца `lesson = {until: далёкое будущее}` + `busy`. Но при первой загрузке вкладки стартовый ростер всё равно пишется в сессию; использовать одноразовый контекст браузера (и так нужен). Груши стоят на острове TRAIN; боец идёт к ним и бьёт (`drill`).

### 5.8 Пятеро на главном острове — есть ограничение
Естественная раскладка для 5 тел: **1 впереди, 2 в середине, 2 сзади**, а не «2 впереди, 3 сзади». Чтобы получить 2+3 надо поменять 6 слотов `HOME_SLOTS` до монтирования (экспортируется и изменяем; под dev-сервером достижимо без правки файла; на prod нужен хук). Состояние `ready` = стоят, лицом к камере, без груш и блуждания — это и есть «стоят». Подписи — DOM `.fighter-tag`, прячутся CSS. Ядер четыре, тел пять (герой сцены 02 + по одному на ядро) — одно ядро повторится у героя; повторы ядер допустимы.

### 5.9 Жест «рука вперёд на камеру» — **снаружи возможен**, правка файла бойца не нужна
Проверено: из обёртки над `renderer.render` выставил `joints.armR.shoulder.rotation.x = 1.5`, `elbow.rotation.x = 0.05` на всех трёх телах — правая рука вытянулась вперёд (`gesture-try.png` против `gesture-off.png`). Условия:
- `update()` каждый кадр перезаписывает x-каналы плеч/локтей/бёдер/коленей и торс, поэтому запись — строго **после** `fighter.update` и **перед** `render`;
- **голова — не сустав** (безымянный короб внутри торса), её поворот к камере — только поворотом торса (`torso.rotation.y`) или добавочной правкой скелета; пальца/кисти нет (предплечье — один блок). Указательный жест получится «рукой-стрелой», а не пальцем;
- каналы `shoulder.rotation.y/z`, `elbow.y/z`, `torso.z` `update()` не пишет — на них можно добавить «подъём в сторону» без конфликта.
Если «рука-стрела» устроит — правка защищённого файла не понадобится. Если нужен именно палец/кисть — это правка файла бойца, стоп по §2.7.

### 5.12 Инструменты
- **ffmpeg:** в песочнице только сборка Playwright — умеет **VP8 и PNG, H.264 нет**. Нашёл обходной путь: `pip download imageio-ffmpeg` скачивается (прокси пускает), внутри статический ffmpeg 7.0.2 **с libx264/libx265**. Для мастера и веб-версии H.264 достаточно. Инструкция для пользователя на своей машине: обычный `ffmpeg` с libx264.
- **Отрисовщик:** Chromium с `SwiftShader` (ANGLE, Vulkan, программный). Реальное время ~7,5 кадр/с на 1280×720 в dev-режиме — для виртуального времени это не важно. Он темнее настоящей видеокарты (см. риск 5).
- Зависимости поставились (`npm install`), dev-сервер `vite` поднимается за секунду, Playwright 1.56 — глобально, не в `package.json` (скрипты игры берут его оттуда же).

### 5.13 Оценка этапов и риски
Оценка в рабочих сессиях (одна сессия ≈ один длинный заход): **этап 1 — 1** (конвейер на одном плане + проверка побитового совпадения + регрессионные суммы), **этап 2 — 2** (режиссёр камеры, сценарий как файл данных, проход всех сцен, журнал событий боя, подбор зерна для легенды), **этап 3 — 2** (переходы T1–T3, постановка пятерых, жест, BAM), **этап 4 — 1–2** (размытие движения, сверка цвета, сборка). ## 6. Открытые риски и вопросы (с рекомендацией)

1. **Финальный рендер — только через dev-сервер.** Причина: обработчики сцен недоступны в prod-сборке. Рекомендация: так и делать, игру не менять. Альтернатива — 4 строки-хука в незащищённых сценах (нужно ваше слово).
2. **Раскладка «2 впереди, 3 сзади» на главном острове.** Потребует подмены 6 слотов до монтирования. Рекомендация: делать подменой из обвязки; если не выйдет — хук.
3. **Жест «рукой-стрелой».** Получится без правки бойца, но не «пальцем». Рекомендация: посмотреть на снимке `gesture-try.png`; если устроит — идём так; если нужен палец — отдельное разрешение на правку файла бойца (добавочную, отдельным коммитом).
4. **Легенда в SQUAD может молчать.** Рекомендация: журнал событий и подбор зерна на этапе 2; если подходящего нет — можно подержать бой дольше или выбрать зерно с ранним уроном.
5. **Цвет.** Песочница рисует программно и темнее видеокарты. Рекомендация: финальный рендер на машине с видеокартой (инструкцию дам).
6. **Шрифты** — нужны локально (раздел 5.10).
7. **Интерфейс в кадре.** Чипы SHOP/кабинет с меткой `SOON`, `EDIT SPACE`, панель бойцов в зале, панели кличей/баффов/«COOLDOWN» на арене — всё это в кадр не должно попасть. Прячем стилями из обвязки; строку решений легенды (`.cmd-line`) оставляем, если ТЗ требует её видеть, иначе оформляем отдельно.
8. **`?showcase=1` не трогаем** — он занят окном боя на деке. Режиму ролика игровой признак не нужен: всё делает обвязка снаружи (своя папка со скриптами).
9. **Что ТЗ сверх текущей игры:** «острова бойцов крупным планом» в воротах мелкие — нужен подлёт камеры (с обвязкой можно). Жеста в игре нет — делаем снаружи.
10. **Сверка с ТЗ §2.4:** легенду над **ареной** не рисуем — согласуется с игрой.
