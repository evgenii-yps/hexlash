# Обвязка рендера showcase-ролика

Отдельная папка. **Игру не меняет ни одной строкой:** обвязка запускает настоящую игру в браузере, подменяет время и случайность, ставит свою камеру и снимает кадры. Всё лежит здесь и в `docs/showcase-trailer/`.

## Как пересобрать ролик (с нуля, на чистой машине)

```
git clone … && cd hexlash
npm install                                   # зависимости игры (нужен vite)
cd tools/showcase && npm install && cd ../..  # шрифты и Playwright для обвязки
node tools/showcase/cli.mjs build             # весь ролик → tools/showcase/out/<план>/*.mp4
```

Другие команды:

```
node tools/showcase/cli.mjs plan <id>                     один план целиком
node tools/showcase/cli.mjs plan <id> --range 60-120      только кадры 60–119 (сцена всё равно считается с начала плана)
node tools/showcase/cli.mjs plan <id> --every 2           каждый 2-й кадр: черновик 30 кадр/с
node tools/showcase/cli.mjs plan <id> --size 1920x1080    размер кадра
node tools/showcase/cli.mjs verify <id>                   ПОЛНАЯ сверка: два независимых рендера и сравнение всех кадров побайтно (только по запросу)
node tools/showcase/cli.mjs fights [duel|squad]           подбор боёв заново (зёрна) → plan/fights.lock.json; `build` делает это сам, если цифры боя в игре изменились
node tools/showcase/cli.mjs excerpts [--reuse]            отрывки переходов T1–T3 и финала в 1080p/30 (`--reuse` — только собрать видео из уже снятых кадров)
node tools/showcase/cli.mjs guard [ref]                   снимки самой игры «до» (ref, по умолчанию origin/main) и «после» (рабочая копия): главный остров, ворота, зал FORGE и бой на арене × 4 раскладки
node tools/showcase/cli.mjs regress [ref]                 регрессионный снимок боя: scripts/fight-regression*.mjs на эталоне и на рабочей копии, выводы и контрольные суммы сравниваются
```

`build` — одна команда на всё: привязка к коммиту `main` (печатается в начале и пишется в `out/trailer/build-info.json`) → при изменении цифр боя подбор боёв заново → кадры всех планов → **выборочная сверка** (второй рендер каждого 10-го кадра плана, побайтно) → шкала → mp4, `marks.json/csv`, `stills/`, `net-report.json`, `verify-report.json`.

Снимки «до/после» сравниваются побайтно; отдельным числом считается «в допуске»: не более 2 уровней яркости на канал и не более 0,1 % пикселей кадра (`GUARD_TOL` в `cli.mjs`; допуск действует ТОЛЬКО для снимков игры — кадры ролика и контрольные суммы боя сверяются строго побайтно).

Сценарий (тайминг, камера, мир) — один файл `plan/trailer.plan.mjs`. Шкала — кадры при 60 кадр/с.

## Что нужно на машине

* **Node 20+**, **Chromium от Playwright** (если браузера нет: `npx playwright install chromium` внутри `tools/showcase`).
* **dev-сервер игры (vite)** обвязка поднимает сама (порт 5199, или возьмёт `SHOWCASE_BASE=http://…`).
  Финальный рендер идёт **только через dev-сервер**: в prod-сборке состояние сцен спрятано, а камера режиссёра его берёт оттуда.
* **ffmpeg с H.264 (libx264).** Обвязка ищет по порядку: `FFMPEG=/путь`, `tools/showcase/.cache`, `ffmpeg` в PATH.
  Если ничего нет — сама скачивает статическую сборку из pip-пакета `imageio-ffmpeg` (`pip download imageio-ffmpeg --no-deps`, внутри ffmpeg 7 с libx264/libx265) и распаковывает в `.cache/`.
  ⚠️ В песочнице Claude системный ffmpeg Playwright умеет только VP8 — H.264 в нём нет, поэтому нужен этот обход.
* **Шрифты** Saira Condensed и JetBrains Mono берутся из npm-пакетов `@fontsource/*` (папка `node_modules` обвязки) и подменяют ответы Google Fonts на уровне сети страницы. Файлов шрифтов в игре нет и не будет.
* **Доступ к сети** для рендера не нужен: всё внешнее (аналитика, кошельки, запросы к модели легенды) обрывается.

## Как устроена воспроизводимость (и почему это важно не ломать)

Задача: два рендера одного плана дают **побайтно одинаковые кадры**. Этого удалось добиться при условии всех пунктов:

1. **Виртуальное время** (`page/clock.js`). `requestAnimationFrame`, `performance.now`, `Date`, таймеры идут только по команде `__vt.step()`; шаг **16,6667 мс**, а не 1000/60 (игра пропускает кадр, если прошло меньше 16,6667 мс).
2. **CSS-анимации** (блеск кнопки FIGHT и т.п.) браузер гонит по своим часам. Каждый кадр прокручиваем их через Web Animations API. Новую анимацию начинаем с нуля **от текущего виртуального момента**, а не с её «настоящего» времени: между созданием и нашим шагом она успевает пробежать несколько реальных миллисекунд, и это число разное от запуска к запуску (из-за него редко, примерно раз в десять запусков, расходились пиксели кнопки). После каждого шага ждём два настоящих кадра браузера, иначе порядок событий `transitionend` зависел бы от скорости машины.
3. **Случайность — два потока.** Игра и сторонние библиотеки (Amplitude с повтором запросов «с дрожью») тянут один `Math.random`; сторонний код вызывается на кадрах, которые зависят от реальной сети, и сдвигал бы весь дальнейший бой на одно число. Вызовы из файлов зависимостей (кроме общих чанков с three) уходят в отдельный поток. Классифицируются два ближайших кадра стека — глубже сидит рантайм Vue, который зовёт и игру.
4. **Якорь постройки сцены.** В момент создания первого WebGL-контекста игровой поток засевается заново, и запоминается номер кадра. План стартует ровно через `align` кадров **после этого якоря** (по умолчанию 420), а не на каком-то кадре страницы: состояние сцены считается от её постройки, а страница успевает загрузиться за разное число кадров.
5. **Окружение.** «Уменьшить движение» выключено (иначе нет пролётов и блуждания), мышь «тонкая», `hardwareConcurrency`/`deviceMemory` = 8 (иначе плотность пикселей режется до 1,5), `deviceScaleFactor` = 1.
6. **Камера режиссёра** (этап 3: добавочные каналы `post` — крен, рывок, подъезд; `platesOff` — скрыть плашки HP; `anchor:'legend'` — ключи от позиции легенды; `stage` — постановка пятерых и жест; `drive:true` — настоящая камера, нужна воротам, потому что подписи островов считает сама сцена; всё описано в шапке `page/director.js`).
7. **Переходы CSS после шага** ставятся на паузу в ноль до снимка (`syncAnimations()` в конце `settle()`): иначе они проживали бы настоящие миллисекунды, зависящие от машины и от частоты снимков.
   Без `drive` режиссёр не правит сцену: оборачивает `renderer.render`, выставляет позу перед отрисовкой и возвращает сценическую после — пролёты, покачивание и OrbitControls вмешательства не замечают.

## Аналитика и сеть

Всё, что уходит за пределы локального dev-сервера, обрывается на уровне сети браузера (`lib/net.mjs`): аналитика (Amplitude, Google Tag Manager), запросы кошельков, WebSocket-и наружу. Шрифты отвечаются локально. Отчёт `out/trailer/net-report.json` содержит список заблокированных адресов и поле `sentOutside` — сколько запросов ушло наружу по-настоящему. Должно быть 0. Код игры для этого не меняется.

## Бои ролика

Бои — настоящие бои движка. `plan/fights.lock.json` хранит выбранные зёрна и окна и привязан к «отпечатку цифр боя» (`lib/provenance.mjs`, sha256 26 боевых файлов). Если отпечаток не совпал, `build` сам прогоняет бои заново, читает журнал событий и подбирает зёрна по критериям из `lib/fights.mjs`. Пороги легенды, HP и состав не трогаются.

## Если кадры перестали совпадать

`cli.mjs verify <id>` покажет первый расходящийся кадр. Дальше — сравнить пиксельную разницу двух прогонов (`out/<план>/run-a`, `run-b`). Выборочная сверка в `build` при расхождении оставляет снимки второго рендера в `out/_verify/<план>`. Частые причины: план заходит на экран загрузки игры (полоса прогресса идёт по реальному времени — план нужно обрезать до него); CSS-переход стартует после действия мыши (см. `__vt.sync()` в `clock.js`); новый сторонний вызов `Math.random`, новая CSS-анимация с событием по завершении, изменение игры так, что постройка сцены стала асинхронной.

## Что не делаем

Не правим файлы игры и не добавляем в игру шрифты, хуки и флаги. `?showcase=1` занят окном боя на деке для инвесторов и здесь не используется.
